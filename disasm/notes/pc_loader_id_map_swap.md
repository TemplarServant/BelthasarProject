# Two of the seven PC loaders had their char ids swapped — on BOTH sides of the check

`ct.exe --vm` compares the C engine's actor placement against the packed actor table in
`ct_assets.dat` over 512 scenes, and reported **512 OK, 0 mismatch**. It was comparing two copies of
the same mistake: every op-`0x68` site loaded **Robo** where the ROM loads **Frog**, and every
`0x6A` the reverse.

---

## 1. THE ROM

The seven one-byte PC loaders hardwire their char id instead of taking an operand. Read out of the
event-op jump table at **`C0:5D6E`**, then each handler's own immediate:

| op | handler | writes | id | |
|---|---|---|---|---|
| 0x57 | C0/41E4 | `STA $8D` | `LDA #00` → 0 | Crono |
| 0x5C | C0/41EC | `STA $8E` | `LDA #01` → 1 | Marle |
| 0x62 | C0/41F4 | `STA $8F` | `LDA #02` → 2 | Lucca |
| **0x6A** | **C0/4204** | `STA $90` | **`LDA #03` → 3** | **Robo** |
| **0x68** | **C0/41FC** | `STA $91` | **`LDA #04` → 4** | **Frog** |
| 0x6C | C0/420C | `STA $92` | `LDA #05` → 5 | Ayla |
| 0x6D | C0/4214 | `STA $93` | `LDA #06` → 6 | Magus |

⭐ **The mapping is NOT monotonic in the handler address.** The EARLIER handler (`41FC`, op 0x68)
carries the HIGHER id (4) and the LATER one (`4204`, op 0x6A) the lower (3). Everything else is in
order — which is precisely the shape that invites arithmetic on the opcode and gets exactly two of
the seven wrong.

`src/move.c`'s graded arm already had this right, in a table, with a comment warning about it:

```c
static const struct { int op, id; } PCIMM[7] = {
  { 0x57, 0 }, { 0x5C, 1 }, { 0x62, 2 }, { 0x6A, 3 },     // 41E4 / 41EC / 41F4 / 4204
  { 0x68, 4 }, { 0x6C, 5 }, { 0x6D, 6 },                  // 41FC / 420C / 4214
};
```

---

## 2. THE SHARED ERROR — why 512/512 proved nothing

Two other copies of the map existed, and **both** had the swap:

* `src/ct_vm.c` `pcSprite()` — the LIVE VM: `case 0x68: return 3; case 0x6A: return 4;`
* `assets/script.py` `_PC` — the PACKER: `{... 0x68: 3, 0x6A: 4 ...}`

`--vm` compares the first against a table built by the second. **A check whose reference is derived
from the same assumption as the thing it checks cannot see an error in that assumption.** The
0x68/0x6A swap sat in a perfectly green 512/512 for as long as both copies agreed.

The tell was that correcting only ONE side made three scenes disagree:

```
MISMATCH scene  87 (script  89): C=4 packed=4
MISMATCH scene 345 (script 309): C=4 packed=4
MISMATCH scene 429 (script  67): C=6 packed=6
```

Counts equal, values different — the sprite id, not the placement.

---

## 3. THE FIX, and the size of it

Both copies now carry the ROM's map. The packer was verified **byte-reproducible first** —
regenerating `ct_assets.dat` with no source change diffs to **0 bytes** — so the rebuild's effect is
attributable to nothing else:

```
differing bytes from the _PC fix: 4  ->  5C0EC0, 5C2F4A, 5C3AE6, 5C3AEE
C VM vs packed actors over 512 scenes: 512 OK, 0 mismatch
```

**Four bytes** in a 13.8 MB file: the four actor sprite entries of the three affected scenes. The
sweep is green again, now on the value the ROM gives.

---

## 4. THE GUARD — because the count line can never catch this class

`--vm` now also prints the engine's own map, and `vm-512-scene-actors` pins it:

```
pcloader map (C0:5D6E + each handler's immediate): 57=0 5C=1 62=2 68=4 6A=3 6C=5 6D=6
```

That line pins ONE side against the ROM independently of the other, so a future re-swap of both
copies is red instead of silent. The mismatch count, by construction, could never do that.

**The general rule this is an instance of:** when a check's reference is generated by our own code,
the check grades the two implementations' AGREEMENT, not their correctness. Pin at least one side
against the ROM directly, or the pair can drift together.

---

## 5. OPEN

* **The other hand-written table in the packer was audited, and it is clean.** `assets/script.py`'s
  only other one is `OPLEN` (the script op lengths, built by the `_set(n, …)` calls). Compared
  opcode by opcode against `src/ct_vm.c`'s `OPLEN[256]`, excluding the eight the engine's `opLen()`
  special-cases as variable-length: **239 opcodes in common, 0 disagreements**, and 17 opcodes the
  packer has no length for at all (`01 2E 4E 88 93 9B BE BF C6 DB E9 EF …`).

  ⚠ Read that as what it is. Agreement between two of our own tables is exactly the evidence that
  was worthless for `_PC`, so it does NOT establish that either is right — only that they have not
  drifted apart. What anchors the lengths to the ROM is a different artefact: `--sweepops`
  micro-executes 210 opcodes and compares the RETURNED IP, so move.c's per-arm arithmetic is
  ROM-graded. Nothing yet ties the packer's `OPLEN` or `ct_vm.c`'s `OPLEN[256]` to that.
  Extracting the sweep's per-opcode IP delta and diffing it against both tables would close it, and
  is the natural next audit.
